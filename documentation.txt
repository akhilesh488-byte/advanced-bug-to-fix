Basic project outline:

1. User submits: prompt + GitHub repo URL
2. clone_repo(url) → if fails, report error to user and stop; else continue
3. run_shell → execute the code once, capture output
4. Classify: does output contain a traceback, or is it a clean run with a value?
        │
        ├── Traceback → skip most of localization, LLM1 mainly parses the trace (still goes through the loop below, but usually converges in 1 turn since the trace hands it the file+line)
        │
        └── Clean run, wrong value → full localization loop needed (see below)
5. Prompt-type routing:
        ├── Function named explicitly → search_code(function_name) extracts it directly, skip most of LLM1's exploration
        └── Vague / a bit specific → LLM1 reads and explores freely (see below)
6. LLM1 loop → produces context packet (JSON)
7. sandbox_manager.create_attempt() → LLM2 works in an isolated worktree, using LLM1's packet
8. LLM2 tries a fix, tests it, reports result
        ├── Pass → hand to LLM3
        └── Fail → sandbox_manager.discard_attempt(), create a new one, LLM2 retries with the failure report from the last attempt included, so it doesn't repeat itself
9. LLM3 verifies independently against the baseline from step 3
        ├── Pass → sandbox_manager.finalize_attempt() → git_push → report_write (success report, markdown)
        └── Fail → report_write (failure report) → ask user: retry? → if yes, loop back to LLM1 with the failure report attached


We will first start with tool creation.
tools:
1. clone_repo: clone the repo inside target_repo folder, if already exist give out a message “repository already exist”, if it doesn’t exist then create a new one, if tool fails return a fail message.
2. run_shell: this is to run the program and check for the output, → problems: terminal may ask for input, the file maybe a jupyter notebook, for v1 version we will skip these two cases and focus only on programs that return a value, and instead of using ‘python’ command to execute the program, which may run it in global python env, so we will use ‘sys.executable’ to run the program in current venv.
3. read_file: this tool will provide llm the entire content of a particular file.
4. search_code: if user provides name of the function or a particular syntax then its best for the llm to have access to a search tool which will return the name of the file that has the particular syntax or the function.
        limitation: There is a problem, if user doesn't provide the accurate syntax as is in the file then this tool is of no use, even a space matters here.
5. edit_file: this will replace a part of the file with the new content, method: take the file path, old content, look for that old content in the file and replace it completely with the new content, the problem: old content may occur more than once, so we have to force llm to provide surrounding context to make the part look unique. 
6. write_file: this is simple, if file does not exist create a new and write the contents, if already exist then replace the content but make sure that llm is aware of this.
7. report_write: llm will pass the reports to each other as context, for visibility its best to write it down in the disk and use it.
        At the end we want to generate a final report for Human review.

## The Mental Model for Agentic Architecture
When deciding where to handle an edge case in your projects, ask yourself one question: Can the LLM reasonably recover from this?

### Put the error handling in the TOOL if:

The AI guessed a bad parameter (e.g., misspelled a file name, bad regex).

The AI needs to try an alternative approach (e.g., tests failed, so it needs to rewrite the code).

Action: Return the error as a string to the LLM so it can try again.

Put the error handling in the GRAPH if:

A prerequisite step entirely failed (e.g., repository didn't clone, database is down).

An LLM agent exceeded its iteration limit or hit a safety filter without producing its required artifact (like a report).

Starting the next node would just be throwing money/compute into a black hole.

Action: Route the graph to an END state or a specific human_intervention node.
